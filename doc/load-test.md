# 負荷・耐性試験と品質指標

> 設計上の根拠: [テスト方針](./designs/19-testing.md) 5節 / [可用性](./designs/18-availability.md) / [セキュリティ実装対策](./designs/11-security-controls.md) 11.2

公開前に「何件までなら壊れないか」「壊れ方は設計どおりか」を**数字で**押さえる。
実行は [`scripts/load-test.mjs`](../scripts/load-test.mjs)。

```bash
pnpm dev                                  # 別ターミナル
pnpm load-test                            # 既定 8対戦 × 6手番
EMERALD_PAIRS=4 EMERALD_TURNS=4 pnpm load-test
```

## 1. 測る対象

| #   | 項目           | 何を見るか                                                                     |
| --- | -------------- | ------------------------------------------------------------------------------ |
| 1   | 同時対戦       | ゲスト発行 → マッチング → チケット → WS 接続 → 布陣 → 手番進行の各段の所要時間 |
| 2   | 再接続集中     | 全接続を同時に切り、チケット再取得と `lastRev` 差分で復帰できるか              |
| 3   | 大量の無効操作 | 規則違反は個別に拒否、**スキーマ違反は連続5件で切断**（設計どおりか）          |
| 4   | ログ書き出し   | 終局 → Queue → consumer → D1/R2 のアーカイブ完了までの時間と取りこぼし         |

**測っていないもの**: ルールエンジンの計算量（Vitest 側の 1,000 seed 生成検証と 100 CPU 対局で見る）、
実ブラウザの描画性能、地理的に分散した接続元からの遅延。

手番進行には `endTurn` を使う。合法手の生成にはエンジン本体が要り、負荷試験スクリプトから
呼ぶと検証対象の二重実装になるため。

## 2. 測定結果（2026-09-07 / ローカル）

環境: Windows 11、`pnpm dev`（Vite + `wrangler dev`）と負荷生成を**同一マシン**で実行。
ローカルの D1 は Miniflare の SQLite で、本番の D1 とは並行性の特性が違う。

| 同時対戦 | 手番 | 完走 | アーカイブ | 経過 | 結果                                       |
| -------- | ---- | ---- | ---------- | ---- | ------------------------------------------ |
| 4        | 4    | 4/4  | 4/4        | 62秒 | **合格**                                   |
| 6        | 4    | 5/6  | 5/5        | 99秒 | 1件が `welcome` 待ちで12秒超のタイムアウト |
| 8        | 6    | 0/8  | —          | —    | 全件が対局開始前に時間切れ終局（3節）      |

4対戦（8接続）時の内訳（ミリ秒）:

| 段             | p50   | p95   | 最大  | 備考                                              |
| -------------- | ----- | ----- | ----- | ------------------------------------------------- |
| ゲスト発行     | 6186  | 6206  | 6206  | 8件を同時に発行した場合                           |
| マッチング     | 9586  | —     | —     | 8人の投入から全員成立まで（1秒ポーリング込み）    |
| チケット       | 1588  | 1724  | 1724  | `POST /matches/{id}/ws-ticket`                    |
| WS 接続        | 2653  | 4344  | 4344  | Upgrade から `welcome` まで                       |
| 布陣           | 2649  | 3248  | 3248  | 両者確定と同時公開まで                            |
| 手番           | 889   | 1318  | 1318  | `endTurn` 送信から相手へ `events` が届くまで      |
| 無効操作の拒否 | 124   | 149   | 149   | 規則違反の Command 1件あたり                      |
| 再接続         | 7420  | 9389  | 9389  | 切断 → チケット再取得 → `welcome` まで（8本同時） |
| アーカイブ     | 13405 | 14946 | 14946 | 投了から `replayAvailable` まで                   |

耐性の確認（全実行で同じ結果）:

- 規則違反の Command 8件は**すべて個別に拒否**され、接続は維持された。
- スキーマ違反のフレームを連発すると**切断された**（`security_event` に `ws_invalid_flood` が4件記録済み）。
- 一斉切断後、8接続すべてが `lastRev` を渡して復帰し、`rev` の後退は起きなかった。

## 3. 分かったこと

### 3-1. ローカルの上限は同時4対戦（8接続）

6対戦で `welcome` が12秒を超え、8対戦では**対局が始まる前に時間切れで終局**した
（全件 `E_MATCH_FINISHED`）。布陣45秒・手番30秒は**実時間の期限**なので、
準備（ゲスト発行6秒＋マッチング16秒＋チケット9秒＋接続12秒）でその予算を食い潰すと、
利用者が何もしていないのに試合が終わる。

これは同一マシンで生成側とサーバを動かしているローカル特有の飽和であり、
**本番の容量を示す数字ではない**。ただし「準備が遅いと期限が先に来る」という
壊れ方そのものは本番でも同じであり、実測は staging で取り直す必要がある（5節）。

### 3-2. 同時終局で D1 が詰まり、Queue の再試行で解消する

複数の対戦が同時に終局すると、ローカルの D1 が `SQLITE_BUSY` を返し、
アーカイブが失敗する。**Queue の自動リトライで最終的に成功し、取りこぼしは0件だった**
（`archive_state` が `failed` のまま残った対戦は無かった）。
[可用性](./designs/18-availability.md) 15.5「Queue の障害」で想定した経路が実際に働いている。

毎時 Cron の再照合はフォールバックとして残る。負荷試験スクリプトは Queue 経路で60秒
待って未完了があれば Cron を叩き、その後さらに60秒待つ（この分岐は今回の測定では
発火しなかった＝Queue 経路だけで片付いた）。

### 3-3. 投了は手番の座席からしか出せない

MatchRoom は非手番の Command を種類を問わず `E_NOT_YOUR_TURN` で弾くため、
**相手の手番中は投了もできない**。仕様として妥当（最大30秒で自分の手番が来る）だが、
画面側で「投了は自分の手番のみ」と分かるようにしておくこと。負荷試験スクリプトも
手番側から投了している。

### 3-4. 無効試合が戦績から外れていなかった（修正済み）

インシデント訓練（[incident-drill](./incident-drill.md) S-1）で発覚。`summarizeRecord` が
`match.status` を見ておらず、`void`（無効試合）にしても勝敗に計上され続けていた。
`match` を join して `status <> 'void'` で除外するよう修正し、`pnpm verify:phase7` の
7番目の検査（対戦→投了→`void` 化→戦績が1件減ること）で回帰を止める。

## 4. 判定基準（公開の可否）

| 指標                               | 基準                       | 現状（ローカル）    |
| ---------------------------------- | -------------------------- | ------------------- |
| 手番の往復（p95）                  | 2秒未満                    | 1.3秒 ✅            |
| WS 接続から `welcome`（p95）       | 5秒未満                    | 4.3秒 ✅（4対戦時） |
| 一斉再接続の成功率                 | 100%                       | 8/8 ✅              |
| アーカイブの取りこぼし             | 0件                        | 0件 ✅              |
| 規則違反の拒否で接続が切れないこと | 切れない                   | 切れない ✅         |
| スキーマ違反の連発で切断されること | 切断される                 | 切断される ✅       |
| 同時対戦数                         | **staging で20対戦を目標** | 未測定 ⏳（5節）    |

## 5. 残っている作業（公開前）

1. **staging での実測**。ローカルの飽和と本番の容量は別物である。
   `EMERALD_WEB_ORIGIN` / `EMERALD_REALTIME_ORIGIN` を staging へ向けて
   `EMERALD_PAIRS=20 pnpm load-test` を流し、本表を staging の数字で更新する。
2. 実ブラウザでの互換性確認（[テスト方針](./designs/19-testing.md) 6節の対応表）。
3. 準備段階が遅いときの利用者向けの見え方（マッチング中の表示、接続失敗時の再試行導線）の確認。

## 6. 品質指標の日常的な見方（公開後）

負荷試験は公開前の一度きりではなく、次の指標で継続的に見る
（[監視](./designs/14-observability.md)）。

| 指標                          | 取得元                                  | 警告の目安            |
| ----------------------------- | --------------------------------------- | --------------------- |
| Worker のエラー率             | Workers Analytics（`observability`）    | 1% 超で調査           |
| WS 接続の失敗率               | realtime の Workers Logs（403/426/429） | 通常時の3倍           |
| `security_event` の warn 以上 | `/admin` の一覧                         | 日次で急増したら調査  |
| アーカイブ滞留                | `match.replay_key IS NULL` の件数       | 6時間で警告           |
| Queue の滞留                  | Queues のダッシュボード                 | 100件超 / 最古1時間超 |
| D1 の書き込み量               | D1 のダッシュボード                     | 無料枠の80%           |
