### 15.1 障害対策（企画書 25）

| 事象 | 対応 |
|---|---|
| クライアント切断 | 60秒の猶予後に相手へ通知、さらに60秒で切断敗北。再接続はチケット再取得＋`lastRev` 差分 |
| DO の再起動 | 状態は SQLite にあるため復元される。ハイバネーション復帰時は `serializeAttachment` から座席を復元 |
| 同じ要求の再送 | `actionId` で冪等化（9.2） |
| DO の異常 | `status = 'void'`（無効試合）へ遷移させ、双方に通知。戦績に計上しない |
| Queue consumer の失敗 | 自動リトライ。規定回数の失敗で DLQ へ送り、運営に通知。DO 側は `archive_state='failed'` を保持し続け、72時間超でアラート |
| ルール更新（デプロイ） | **デプロイは DO を再起動し、進行中の WS 接続をすべて切断する**（Cloudflare 仕様）。試合状態自体は SQLite にあるため失われないが、参加者は一斉に切断を経験するため、クライアントの自動再接続で復帰させる。ルール実装は 8.4 の版数レジストリにより、再起動後も試合開始時の `RULE_VERSION` のまま継続できる |
| ロールバック | Worker ごとに独立してロールバック可能（Cloudflare の versions / rollback）。ロールバックも DO を再起動させる点はデプロイと同様 |

### 15.2 データ保護

- アカウント削除: 論理削除（`deleted_at`）→ 30日後に個人情報（メール、表示名、認証情報）を物理削除。対戦履歴は `user_id` を匿名化した形で統計目的のみ保持する。この方針は利用規約とプライバシーポリシーに明記する。
- バックアップ: D1 の Time Travel を利用する。**訂正**: 保持日数はプランに依存し、**Workers Free プランでは過去7日、Workers Paid プランでは過去30日**（[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)）。本プロジェクトは無料プランを前提とするため実質7日である。これだけでは監査ログ400日・運営操作履歴3年の保持方針（13.3）を満たせないため、**週次で D1 の主要テーブルを R2 へエクスポートするバッチ**を別途設け、Time Travel を超える期間の復旧はこのエクスポートから行う。四半期ごとに復旧手順を検証する。
- 本番データは開発・ステージングへコピーしない。

### 15.3 環境分離

| 環境 | Worker 名 | D1 | 用途 |
|---|---|---|---|
| local | — | ローカル Miniflare | 開発 |
| staging | `emerald-wani-web-stg` / `emerald-wani-realtime-stg` | `emerald-wani-db-stg` | 検証・E2E |
| production | `emerald-wani-web` / `emerald-wani-realtime` | `emerald-wani-db` | 本番 |

- DO 名前空間は Worker 名に紐づくため、Worker 名を分けることで環境が完全に分離される。
- シークレットは環境ごとに個別に投入する。
- 本番デプロイは段階的に行い、`observability.enabled = true` でログとメトリクスを取得する。

## 15.4 RPO / RTO と復元試験

「バックアップがある」だけでは復旧できない。**どこまでのデータ損失を許容し、いつまでに復旧するか**を対象ごとに定める。

| 対象 | RPO（許容データ損失） | RTO（目標復旧時間） | 復旧手段 | 復旧担当 |
|---|---|---|---|---|
| ユーザー・アカウント情報 | 24時間 | 4時間 | D1 Time Travel（無料プランは7日）＋週次 R2 エクスポート | プロジェクトオーナー |
| デッキ・所有カード | 24時間 | 8時間 | 同上 | プロジェクトオーナー |
| 対戦結果（`match` / `match_player`） | 24時間 | 8時間 | 同上。欠落分は該当試合を「記録なし」として扱う | プロジェクトオーナー |
| 進行中の対戦（DO 内の状態） | **0（損失を許容しない）** | 即時（自動） | DO の内蔵 SQLite により自動復元。DO 消失時は当該試合を `void` とする | 自動 |
| リプレイ（R2） | 0 | 24時間 | `archive_state` の再照合（Cron）で再生成 | 自動＋オーナー確認 |
| 監査ログ | 24時間 | 72時間 | 週次 R2 エクスポート | プロジェクトオーナー |

### 復元試験

**四半期ごとに、実際に復元を実行して検証する。** 手順書の存在だけでは復旧できたことにならない。

1. staging 環境に、本番と同じ手順で D1 バックアップから復元する（本番データは使わず、同等規模のダミーデータで行う）。
2. 復元後にアプリが正常動作することを E2E テストで確認する。
3. 所要時間を計測し、RTO を満たしているか判定する。
4. 手順の不備を発見したら手順書を改訂し、次回に持ち越さない。

試験の実施記録（日付・担当・所要時間・発見事項）を残す。

## 15.5 想定する障害シナリオ

| シナリオ | 検知 | 対応 |
|---|---|---|
| Cloudflare 側の広域障害 | Worker エラー率の監視（[監視](./14-observability.md)） | 復旧を待つ。進行中の試合は DO の状態から復元される。長時間に及ぶ場合はお知らせで告知 |
| 誤デプロイ（機能不全） | デプロイ後のエラー率監視 | Cloudflare の versions / rollback で即時ロールバック。**ロールバックも DO を再起動する**ため、再接続の集中を想定する |
| D1 の誤更新（誤ったマイグレーション等） | 整合性チェック、利用者からの報告 | Time Travel で誤更新の直前へ復元。復元により失われる正常な更新の範囲を事前に見積もる |
| Queue の障害・メッセージ消失 | Queue 滞留と `archive_state` の監視 | Cron による再照合で DO から直接再取得（[プラン制約](./03-tech-stack.md)）。無料プランの24時間保持を前提に、6時間で警告する |
| R2 への保存失敗 | `archive_state` が `failed` のまま滞留 | 再試行。恒久的に失敗する場合は当該試合を「リプレイなし」として記録し、結果自体（D1）は保持する |
| 対戦結果とリプレイの不整合 | 定期的な照合バッチ | **どちらが正か判断できない場合は当該試合を無効試合（`void`）として扱い、戦績から除外する。** 参加者へ告知する |

対戦結果とリプレイの保存状態が食い違う可能性を設計として認め、**無効試合として処理できる経路を必ず用意する**。整合しないまま戦績に計上することは、保護目的 P-3（一貫性）と P-4（追跡可能性）の両方を損なう。

## 15.6 サービス終了時の扱い

終了は必ず訪れるため、あらかじめ定めておく。

| 項目 | 方針 |
|---|---|
| 事前告知 | 終了の**90日前**までに、お知らせ機能と登録メールアドレスへ通知する |
| データ取得期間 | 告知から終了日まで、利用者が自分のデータ（プロフィール、デッキ、対戦履歴）をエクスポートできる機能を提供する |
| アカウント・個人情報 | サービス終了日から**30日後**に物理削除する |
| 戦績・対戦結果 | 終了日から30日後に削除（個人と結び付かない統計値のみ、匿名化して保持してよい） |
| リプレイ（R2） | 終了日をもって配信停止。30日後に削除 |
| 監査ログ | 法令上または紛争対応上の必要がある場合を除き、**元の保持期間（400日 / 3年）を満了した時点で削除**する。終了によって早期削除しない |
| 課金がある場合 | 未消化分の扱いを利用規約に事前に明記する（MVP では課金なし） |

この方針は利用規約とプライバシーポリシーに反映し、サービス開始時点から公開しておく。
