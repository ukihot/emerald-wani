# インシデント対応と証拠保全

> [設計ドキュメント索引](./README.md)

セキュリティ事故を完全に防ぐことだけを目標にせず、**発生時に影響を限定し、調査でき、復旧できること**を重視する。

## 1. 対応の流れ

すべてのインシデントで次の6工程を踏む。工程ごとに担当と完了条件を記録する。

| 工程        | 内容                                                                                                                                 | 完了条件                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 1. 初動     | 検知の確認、影響範囲の暫定判断、対応チームの招集、**証拠保全の開始（2節）**                                                          | 事象が実在すると確認され、証拠が保全された           |
| 2. 調査     | ログ・リプレイ・監査ログからの原因究明                                                                                               | 侵入経路と影響を受けたデータ・アカウントが特定された |
| 3. 封じ込め | 攻撃の継続を止める（鍵の失効、アカウント停止、機能の一時停止）                                                                       | 攻撃が継続していないことを確認できた                 |
| 4. 復旧     | 正常な状態への回帰（[可用性](./18-availability.md)の復旧手順を使用）                                                                 | サービスが正常に動作し、データ整合性を確認できた     |
| 5. 告知     | 利用者・関係者への通知                                                                                                               | 影響を受けた利用者へ通知が到達した                   |
| 6. 再発防止 | 恒久対策の実施と、**[脅威モデル](./12-threat-model.md)・[テスト](./19-testing.md)・[監視](./14-observability.md)・運用手順への反映** | 個別修正で終わらせず、4つの文書すべてに反映された    |

工程6を省略しないこと。個別修正だけで閉じたインシデントは、同種の再発を招く。

## 2. 証拠保全

**調査前に保全する。** 復旧作業でログや状態が失われると原因究明ができなくなる。

| 対象            | 保全方法                                                                                                                | 注意                                         |
| --------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 対戦の状態      | 該当 `MatchRoom` DO の `archive_state` を `pending` で固定し、**自動削除を止める**（[DO設計](./07-durable-objects.md)） | 通常の10分後削除に流されないよう最優先で実施 |
| リプレイ        | R2 の該当オブジェクトに削除保護（別プレフィックスへコピー）                                                             | 保持期間90日の自動削除より前に退避           |
| 監査ログ        | 該当期間の `security_event` / `admin_audit` を R2 へエクスポート                                                        | 保持期間満了に備える                         |
| Worker ログ     | Workers Logs から該当期間を抽出して保存                                                                                 | 保持が短いため最優先                         |
| Cloudflare 設定 | 該当時点の設定内容と Cloudflare 監査ログを取得                                                                          | 設定改ざんの調査に必要                       |

証拠には**取得時刻・取得者・取得方法**を添えて記録する。

## 3. シナリオ別の初動

| シナリオ                           | 初動（最初の30分）                                                                                                 | 封じ込め                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| **アカウント侵害**                 | 該当ユーザーの全セッションを失効。侵害後の対戦・設定変更を洗い出す                                                 | パスワード再設定を強制。侵害中に行われた変更を必要に応じて巻き戻す                                |
| **管理者侵害**                     | 該当管理者アカウントを即時停止。**Cloudflare Access のポリシーから除外**。`admin_audit` から実行された全操作を抽出 | 全管理者の MFA 再登録。`BETTER_AUTH_SECRET` のローテーション要否を判断                            |
| **署名鍵漏えい（WSチケット）**     | [鍵ライフサイクル](./13-secrets-lifecycle.md) 3節に従い**旧鍵を併用期間なしで即時失効**。進行中の全 WS 接続を切断  | 全ユーザーに再接続（＝チケット再取得）を要求。不正接続の痕跡を調査                                |
| **秘匿情報漏えい（公開前の布陣）** | 漏えい経路（射影バグ / WS配信 / ログ）を特定し、該当機能を即時停止                                                 | 影響範囲の試合を特定し無効試合化。射影処理を修正する                                              |
| **対戦結果の不整合**               | 該当試合を `void`（無効試合）へ遷移。戦績への計上を止める                                                          | `command_log` から再計算し、正しい結果を確定。差分の原因をルールエンジンのバグとして修正          |
| **リプレイ消失**                   | 消失範囲を特定。`archive_state` が `failed` の試合を洗い出す                                                       | Cron の再照合で復旧を試み、不可能なら当該試合を「リプレイなし」として記録（結果自体は D1 に残る） |
| **サービス妨害**                   | WAF での遮断ルール追加、レート制限の一時強化                                                                       | 攻撃元の傾向を分析し、恒久ルールへ反映                                                            |

## 4. 利用者への告知

| 事象                                 | 告知範囲                     | 目安期限               |
| ------------------------------------ | ---------------------------- | ---------------------- |
| 個人情報（メールアドレス等）の漏えい | 影響を受けた利用者全員＋公表 | 事実確認から72時間以内 |
| 秘匿情報（公開前の布陣）の漏えい     | 影響を受けた対戦の参加者     | 事実確認から1週間以内  |
| 対戦結果の誤り・無効試合化           | 該当試合の参加者             | 判断確定後すみやかに   |
| サービス停止                         | 全利用者（お知らせ機能）     | 停止中および復旧時     |

告知には、**何が起きたか・影響範囲・利用者が取るべき行動・再発防止策**を含める。原因が未確定の段階でも、判明している事実と調査中である旨を伝える。

## 5. アカウント停止の記録と異議申立て

不正対策によるアカウント停止は、誤判定の可能性を前提に運用する（[監視](./14-observability.md) 4節の段階的対応）。

### 5.1 記録必須項目

停止を実行する際、`admin_audit` に次を必ず記録する。

| 項目     | 内容                                                           |
| -------- | -------------------------------------------------------------- |
| 根拠     | 判定の元になった `security_event` の ID 群、検知ルール、観測値 |
| 判断者   | 自動判定か、人間による判断か（人間の場合は管理者ID）           |
| 期間     | 一時停止の期限、または恒久停止である旨                         |
| 通知     | 利用者へ通知した日時と内容                                     |
| 解除理由 | 解除した場合、その理由と判断者                                 |

**根拠を記録せずに停止してはならない。** 根拠のない停止は、異議申立てへの回答も再発防止もできない。

### 5.2 異議申立て

- 停止された利用者には、停止の事実と**異議申立ての手段**を通知する。
- 申立ての受付窓口は[脆弱性の受付窓口](./20-vuln-disclosure.md)とは別に用意する（問い合わせフォームまたはメール）。
- 再審査は、**当初の判断者以外**が根拠を確認して行う。
- 誤判定と判明した場合は、速やかに解除し、失われた戦績を復旧する。加えて判定ロジックを見直し、その結果を[監視](./14-observability.md)の閾値と[脅威モデル](./12-threat-model.md)へ反映する。
- 目標期間: 申立て受領の確認は3営業日以内、再審査の結論は14日以内。
