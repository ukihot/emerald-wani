# 鍵・シークレットのライフサイクル

> [設計ドキュメント索引](./README.md)

シークレットを「`wrangler secret put` で入れた」で終わらせず、**用途・所有者・保管場所・環境・ローテーション周期・緊急失効手順**まで台帳として管理する。

## 1. 台帳

| ID   | シークレット                   | 用途                                                                                    | 保管場所                                  | 環境                    | ローテーション周期               | 漏えい時の影響                                                                                 |
| ---- | ------------------------------ | --------------------------------------------------------------------------------------- | ----------------------------------------- | ----------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------- |
| S-01 | `WS_TICKET_SECRET_v<N>`        | WebSocket 接続チケットの HMAC 署名（[セキュリティ実装対策](./11-security-controls.md)） | 両 Worker の Secrets（`wrangler secret`） | stg / prod 個別         | 90日、または漏えい時即時         | 任意ユーザーとして任意の試合に接続可能（P-2 真正性の全面喪失）                                 |
| S-02 | `BETTER_AUTH_SECRET`           | セッション・トークンの署名（better-auth）                                               | web Worker の Secrets                     | stg / prod 個別         | 180日、または漏えい時即時        | 全ユーザーのセッション偽造が可能                                                               |
| S-03 | `TURNSTILE_SECRET_KEY`         | Turnstile siteverify                                                                    | web Worker の Secrets                     | stg / prod 個別         | Cloudflare 側で再発行可能。年1回 | Bot 対策の迂回（トークン検証の偽装は不可だが、鍵の悪用で自サイト以外での検証消費が起こりうる） |
| S-04 | メール配送 API キー            | 確認・再設定メールの送信（[認証・認可設計](./10-auth-and-access.md)）                   | web Worker の Secrets                     | stg / prod 個別         | 90日                             | 自ドメインを騙るメール送信（フィッシングへの悪用）                                             |
| S-05 | `CLOUDFLARE_API_TOKEN`（CI用） | CI からのデプロイ、D1 マイグレーション                                                  | GitHub Actions の Environment secrets     | prod 用は保護環境に限定 | 90日                             | インフラ全体の掌握（T-INFRA-02）                                                               |
| S-06 | `AUDIT_SALT_SECRET`            | `ip_hash` / `ua_hash` の生成（[データモデル](./08-data-model.md)）                      | **両 Worker** の Secrets                  | stg / prod 個別         | 180日、または漏えい時即時        | 過去の IP ハッシュに対する逆引き（レインボーテーブル攻撃）が容易になる                         |
| S-07 | `ALERT_WEBHOOK_URL`            | 重大度 error 以上の通知先（[監視](./14-observability.md) 3節）                          | web Worker の Secrets（realtime も同値）  | stg / prod 個別         | 通知先の再発行時                 | 第三者が偽の警告を運営チャンネルへ流し込める（実害は限定的だが調査を妨げる）                   |

`.dev.vars` に入るローカル開発用の値は、**本番と異なるダミー値**とする。本番の値をローカルへコピーしない（[開発環境](./04-dev-environment.md)）。

**S-06 の「日次ローテート」の実装（フェーズ6）**: 秘密そのものを毎日入れ替えるのではなく、
`HMAC(AUDIT_SALT_SECRET, "audit-v1|<UTCの日付>|<値>")` のように**日付を入力へ混ぜる**。
翌日以降は同じ IP でも別のハッシュになるため「長期追跡ができない」という目的は同じまま満たせて、
秘密を回転させる仕組み（KV と回転ジョブ）を持たずに済む。両 Worker に同じ値を投入すれば、
同日内なら web と realtime のログを突き合わせられる。用途を混ぜないよう接頭辞で分離している
（実装は `src/lib/protocol/audit.ts`）。

## 2. 鍵識別子（kid）と併用期間

署名鍵（S-01）は**識別子付きで複数世代を同時に保持**する。これがないとローテーション時に全接続が失敗する。

```
payload = { kid: "v2", mid, uid, seat, jti, exp, rv }
hmac    = HMAC-SHA256(secret[kid], rawBytesOf(payload))
```

| 段階          | 発行に使う鍵 | 検証で受け付ける鍵 | 期間                                                  |
| ------------- | ------------ | ------------------ | ----------------------------------------------------- |
| 1. 新鍵の配備 | v1（旧）     | v1, v2             | 新鍵を両 Worker へ投入した直後                        |
| 2. 発行の切替 | **v2（新）** | v1, v2             | 切替後10分間（チケット `exp` は60秒のため十分な猶予） |
| 3. 旧鍵の撤去 | v2           | **v2 のみ**        | 切替から10分経過後                                    |

- **両 Worker に同時に鍵を投入してから**発行を切り替える。片方だけ更新された状態で切り替えると検証が失敗する。
- 段階2の期間中は、v1 で署名されたチケットも受理される。これによりローテーション中の接続断を避ける。
- `kid` が未知の値だった場合は即座に拒否し、`security_event` に記録する（鍵の推測試行の可能性）。

`BETTER_AUTH_SECRET`（S-02）のローテーションは、better-auth のセッション互換性の扱いを実装時に確認したうえで、**全セッション失効を伴う計画メンテナンス**として実施する。予告なしに行わない。

## 3. 漏えい時の失効判断

鍵を交換するだけでは不十分な場合がある。**どこまで失効させるか**を鍵ごとに事前に決めておく。

| 漏えいした鍵          | 鍵の交換                          | 併せて失効させるもの                                                                                       | 判断理由                                                         |
| --------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| S-01 WSチケット鍵     | 即時（旧鍵の併用期間を設けない）  | 発行済みの全チケット（`exp` 60秒のため自然失効を待ってもよいが、進行中の全 WS 接続を切断して再認証させる） | 任意の試合への成りすまし接続が可能なため、猶予を与えない         |
| S-02 認証 secret      | 即時                              | **全ユーザーの全セッション**。再ログインを要求する                                                         | セッション偽造が可能なため、既存セッションを信用できない         |
| S-03 Turnstile secret | Cloudflare ダッシュボードで再発行 | なし                                                                                                       | トークン検証はサーバ側で行われるため、既存ユーザーへの影響はない |
| S-04 メールAPIキー    | 即時                              | なし（ただし当該キーで送信された履歴を確認し、フィッシングの有無を調査）                                   | 送信元の悪用調査が主眼                                           |
| S-05 CFトークン       | 即時                              | 当該トークンで行われた変更の全棚卸し（Cloudflare 監査ログ）                                                | インフラ設定の改ざんの有無が最重要                               |
| S-06 IPソルト         | 翌日の自動ローテートを待たず即時  | なし                                                                                                       | 将来の逆引きを止めれば足りる                                     |

失効を実行したら、その事実・時刻・対象範囲を[インシデント対応](./15-incident-response.md)の記録に残す。

## 4. 運用規約

- **ソースコードにも `wrangler.jsonc` にもシークレットを書かない。** `vars` に置いてよいのは公開前提の値（`PUBLIC_TURNSTILE_SITE_KEY` など）のみ。
- シークレットの値をログ・エラーメッセージ・監査ログに出力しない。出力してよいのは `kid` などの識別子まで。
- CI の脆弱性・秘匿値スキャン（[サプライチェーン](./16-supply-chain.md)）でコミット内の秘匿値混入を継続的に検査する。
- ローテーション期限は暦で管理し、期限の2週間前に通知する。期限超過は[監視](./14-observability.md)の警告対象とする。
- 環境ごとに完全に別の値を使う。stg の鍵で prod のチケットが検証できてはならない。
