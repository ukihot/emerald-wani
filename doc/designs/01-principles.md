# 設計原則と保護目的

> [設計ドキュメント索引](./README.md)

## 1. 全体方針

企画書「34. 開発上の重要原則」を設計制約として明文化する。

1. **クライアントは一切信用しない。** クライアントは「〜したい」という要求のみを送る。結果は指定できない。
2. **正はサーバのみが持つ。** ブラウザ側は演出の予告（`predictView`）のみを行い、サーバのイベントで必ず上書きされる（[ルールエンジン設計](./06-rule-engine.md)）。
3. **1試合＝1 Durable Object。** 行動は DO 内で直列に処理する。
4. **ルールエンジンは Cloudflare に依存しない純粋 TypeScript。** `src/lib/game/` は `fetch` も `env` も `Date.now()` も参照しない。時刻・乱数は引数で注入する。これにより単体テストが容易になり、企画書「33. リスク：Cloudflare固有機能への依存」に対応する。
5. **ゲームルールと永続化を分離する。** ルールエンジンは状態とイベントを返すだけ。保存は DO / Queue / D1 の層が行う。
6. **セキュリティは後付けしない。** 認可・検証・レート制限・監査は各エンドポイントの実装テンプレートに最初から組み込む（[セキュリティ実装対策](./11-security-controls.md)）。
7. **「すぐ遊べること」もセキュリティ要件として扱う。** 登録やログインを強制して体験を損なうことは、この設計における失敗とみなす。詳細は下記 3 と[認証・認可設計](./10-auth-and-access.md)。

## 2. 保護目的（ゲーム固有の性質）

一般的な機密性・完全性・可用性に加えて、本サービスが守るべき性質を次のとおり明示する。以降のすべての設計判断は、この5つのどれを守るためのものかを説明できなければならない。

| ID | 性質 | 定義 | 主な実現手段 |
|---|---|---|---|
| **P-1** | **公平性** | 登録状態、通信環境、クライアント改造などによって不当な優位を得られないこと | サーバ権威型（原則1・2）、ゲストと本登録で同一のルール・マッチング基盤（3節）、全行動の再検証（[DO設計](./07-durable-objects.md)） |
| **P-2** | **真正性** | すべての行動が正しい参加者によるものとして確認できること | WSチケットの署名・単回使用、座席認可、`actionId` による冪等化（[セキュリティ実装対策](./11-security-controls.md)） |
| **P-3** | **一貫性** | 両プレイヤーとサーバで勝敗や盤面の認識が食い違わないこと | 状態リビジョン（rev）による楽観ロック、`E_STALE_REV` 時の強制再同期、`command_log` を正本とする決定論再現 |
| **P-4** | **追跡可能性** | 問題が発生した場合に、対戦経過と運営操作を事後確認できること | `command_log` / `event_log` / R2 リプレイ / `security_event` / `admin_audit`（[監視・異常検知](./14-observability.md)） |
| **P-5** | **秘匿性** | 相手の手札、デッキ順、乱数シードなどが許可なく開示されないこと | 座席ごとの射影（`project` / `projectEvent`）、シードの非送信、R2 の座席別射影版の分離保存 |

### 2.1 対象とする不正行為

上記の保護目的に対する脅威として、以下を明示的に対象とする。個々の対策と残留リスクは[脅威モデル](./12-threat-model.md)で整理する。

| 不正行為 | 侵害される性質 |
|---|---|
| クライアント改造（改変したリクエストの送信） | P-1 公平性 / P-2 真正性 |
| Bot・自動操作による対戦またはアカウント大量作成 | P-1 公平性 |
| 複数アカウントの併用（マルチアカウント） | P-1 公平性 |
| 意図的な切断による敗北回避 | P-1 公平性 / P-3 一貫性 |
| 戦績操作・談合（意図的な勝ち星の譲渡） | P-1 公平性 |
| 招待コードの総当たり | P-2 真正性 / P-5 秘匿性 |
| 将来引くカードの順序推測 | P-5 秘匿性 / P-1 公平性 |
| リプレイ・ログの改ざんまたは消失 | P-4 追跡可能性 |
| 相手の手札・デッキ順の推測または漏えい | P-5 秘匿性 |

## 3. 「すぐ遊べること」をセキュリティ要件として扱う

セキュリティを強化する一方で、**登録やログインを強制して体験を損なわないこと**を同格の要件とする。「安全にするために面倒にする」という設計は、本プロジェクトでは採らない。

### 3.1 要件

- トップ画面の「すぐ遊ぶ」から、メールアドレスやパスワードを入力せずにゲストとして対戦を開始できる。
- ユーザーから見ればログイン不要だが、**サーバ内部では匿名ユーザーとして識別し、通常の認証済みセッションと同様に権限管理・不正対策・監査を行う。** 「ゲストだから検証が緩い」経路を作らない。
- ゲストと本登録ユーザーは**同じルール・同じマッチング基盤**で対戦する。ゲスト専用の隔離環境にはしない。
- 登録の有無によって**対戦上の有利・不利を設けない**（P-1 公平性）。

### 3.2 帰結として設計に課される制約

| 制約 | 理由 |
|---|---|
| 認可ガード（[認証・認可設計](./10-auth-and-access.md)）の `auth: 'anonymous'` は「検証しない」ではなく「匿名ユーザーとして認証済み」を意味する | ゲスト経路が検証の抜け穴にならないようにする |
| ゲストにも推測困難な内部ID（UUIDv7）と自動生成の表示名を割り当てる | P-2 真正性。連番IDでゲストを列挙できないようにする |
| ゲストの行動も `security_event` の監査対象に含める | P-4 追跡可能性 |
| ゲストも通報・ブロックの対象とする | 悪質なゲストが無責任に振る舞える状態を作らない |
| 同一ブラウザでは一定期間デッキ・戦績を引き継ぐが、**Cookie を失った場合は復旧できないことを UI で明示する** | 誤解による問い合わせと、復旧を騙る攻撃の両方を防ぐ |
| 本登録時は所有カード・デッキ・戦績・設定を安全に引き継ぐ | 登録の動機を削がないため。移行処理の詳細は[認証・認可設計](./10-auth-and-access.md) |

### 3.3 将来のランク戦との関係

ランク戦を導入する場合も、**ゲストに内部 MMR を持たせることで本登録ユーザーとの対戦を可能にする**（マッチングプールを分断しない）。ただし次は本登録を条件としてよい。

- ランキングへの掲載
- シーズン報酬の受領
- 長期的な戦績の保存

これは「対戦上の有利・不利」ではなく「記録と報酬の永続性」の差であり、3.1 の原則と矛盾しない。
