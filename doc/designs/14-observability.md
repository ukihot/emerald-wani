# 監視・異常検知

> [設計ドキュメント索引](./README.md)

**ログを保存するだけでは監視ではない。** どの状態を異常と判断し、誰へどの期限で通知するかを定める。ログの保存形式そのものは[API とプロトコル](./09-api-protocol.md)、保存先スキーマは[データモデル](./08-data-model.md)を参照。

## 1. 監査ログの対象と保護

### 1.1 記録する事象

| 分類 | 事象                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------ |
| 認証 | ログイン成功・失敗、ログアウト、ゲスト発行、本登録への昇格、パスワード変更、メール変更、セッション失効 |
| 認可 | 権限変更、管理者操作、他人のリソースへのアクセス試行                                                   |
| 対戦 | 不正な Command（`E_FORBIDDEN` / `E_NOT_YOUR_TURN` などの連発）、WS 認証失敗、強制切断、client desync   |
| 運用 | レート制限到達、データエクスポート、アカウント削除、アカウント停止と解除                               |
| 基盤 | Queue 滞留、DLQ 投入、リプレイ未保存、DO 例外                                                          |

### 1.2 相関のための必須項目

調査時に事象をつなげられるよう、**すべてのログ行に次を持たせる**。

| 項目         | 内容                                                   |
| ------------ | ------------------------------------------------------ |
| `ts`         | UTC のミリ秒。時刻はサーバ基準に統一する               |
| `request_id` | 1リクエスト（または1 WS フレーム処理）に採番する相関ID |
| `user_id`    | 匿名ユーザーを含む。未認証時は `null`                  |
| `match_id`   | 対戦に関わる事象のみ                                   |
| `action`     | 操作種別の列挙値                                       |
| `result`     | `ok` / エラーコード                                    |
| `severity`   | `info` / `warn` / `error` / `critical`                 |

### 1.3 記録してはならない項目

Cookie、パスワード、認証トークン、WSチケット、メールアドレス、公開前の相手布陣、生の IP アドレス、生の User-Agent。

IP と User-Agent は[データモデル](./08-data-model.md)の方式（日次ローテートするソルトでの HMAC）でハッシュ化した値のみを保存する。

### 1.4 ログの保護

- `security_event` / `admin_audit` は**追記専用**。API に更新・削除の手段を実装しない。
- 保持期間超過分の削除は運用バッチのみが行い、その実行自体も記録する。
- **ログの閲覧自体を監査対象とする**（管理者が誰のログをいつ見たか）。
- 不正検知用ログとデバッグログを分離し、保持期間を分ける（デバッグログ7日 / 監査ログ400日）。

## 2. 監視項目と警告基準

各項目に**警告基準・重大度・通知先・確認期限**を定める。基準値は MVP の初期値であり、[誤検知の実績](#4-誤検知への備え)に応じて調整する。

### 2.1 認証・アカウント

| 監視項目                       | 警告基準                                                                            | 重大度 | 通知先              | 確認期限  |
| ------------------------------ | ----------------------------------------------------------------------------------- | ------ | ------------------- | --------- |
| ログイン失敗率                 | 全体の失敗率が10分平均で 30% 超                                                     | warn   | 運営 Slack          | 翌営業日  |
| 単一アカウントへのログイン失敗 | 同一 `user_id` に 10分で 20回超                                                     | warn   | 運営 Slack          | 翌営業日  |
| ゲスト発行数                   | 同一 `ip_hash` から1時間に 3件超（[専用DO](./07-durable-objects.md)が拒否した件数） | warn   | 運営 Slack          | 翌営業日  |
| ゲスト発行数（全体）           | 1時間の総発行数が平常時の 5倍超                                                     | error  | 運営 Slack + メール | 4時間以内 |
| 管理者ログイン                 | **全件を通知**（成功・失敗とも）                                                    | warn   | 運営 Slack          | 即時確認  |

### 2.2 対戦とゲーム整合性

| 監視項目                         | 警告基準                                        | 重大度   | 通知先                     | 確認期限                                |
| -------------------------------- | ----------------------------------------------- | -------- | -------------------------- | --------------------------------------- |
| WS 認証失敗                      | 10分で 50件超、または同一 `user_id` から 10件超 | warn     | 運営 Slack                 | 翌営業日                                |
| 不正 Command                     | 同一 `user_id` が1試合で 10件超                 | warn     | 運営 Slack                 | 翌営業日                                |
| client desync                    | 発生率が全試合の 1% 超                          | error    | 運営 Slack                 | 4時間以内（P-3 一貫性の侵害を示すため） |
| 3連続時間切れによる敗北          | 全試合の 5% 超                                  | warn     | 運営 Slack                 | 翌営業日                                |
| 対戦中の切断率                   | 平常時の 2倍超                                  | error    | 運営 Slack                 | 4時間以内                               |
| 布陣公開前の射影に相手配置が混入 | **1件でも検知**                                 | critical | 即時電話相当（オンコール） | 即時（P-5 秘匿性の侵害）                |

### 2.3 永続化と基盤

| 監視項目        | 警告基準                                                    | 重大度          | 通知先     | 確認期限                                    |
| --------------- | ----------------------------------------------------------- | --------------- | ---------- | ------------------------------------------- |
| Queue 滞留      | 未処理メッセージが 100件超、または最古が 1時間超            | error           | 運営 Slack | 4時間以内（無料プランの保持は24時間のため） |
| DLQ 投入        | **1件でも検知**                                             | error           | 運営 Slack | 4時間以内                                   |
| リプレイ未保存  | `archive_state` が `pending`/`failed` のまま 6時間超        | error           | 運営 Slack | 4時間以内                                   |
| DO 例外         | 10分で 10件超                                               | error           | 運営 Slack | 4時間以内                                   |
| D1 日次上限     | 無料枠の 70% / 90% 到達（[プラン制約](./03-tech-stack.md)） | warn / critical | 運営 Slack | 90%到達時は即時                             |
| Worker エラー率 | 5分平均で 1% 超                                             | error           | 運営 Slack | 即時                                        |

### 2.4 運営操作

| 監視項目                         | 警告基準                          | 重大度 | 通知先                         | 確認期限 |
| -------------------------------- | --------------------------------- | ------ | ------------------------------ | -------- |
| 管理者による大量閲覧             | 1時間に 100件超のユーザー情報参照 | warn   | 運営 Slack（本人以外にも通知） | 翌営業日 |
| データエクスポート               | **全件を通知**                    | warn   | 運営 Slack                     | 即時確認 |
| アカウント停止・解除             | **全件を通知**                    | info   | 運営 Slack                     | —        |
| シークレットのローテーション期限 | 期限の2週間前                     | info   | 運営 Slack                     | 期限まで |

## 3. 実装手段

無料プランの範囲で構成する。

- **Workers Logs / `observability.enabled = true`** による構造化ログの収集。
- 重大度 `error` 以上は、Worker から運営の通知先（Slack Incoming Webhook 等）へ直接送る。通知の送信自体が失敗してもリクエスト処理を妨げないよう、`ctx.waitUntil()` で非同期に行う。
- 集計が必要な項目（発生率・平均）は、Cron Trigger で定期的に D1 を集計して閾値判定する。
- 通知先が輻輳しないよう、**同一種別の通知は10分間まとめる**（バースト抑制）。

## 4. 誤検知への備え

**検知しただけで直ちにアカウントを恒久停止しない。** 段階的に対応する。

| 段階 | 対応                                                   | 可逆性                                                                                                                               |
| ---- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | 記録のみ（`security_event`）                           | —                                                                                                                                    |
| 2    | 追加確認（Turnstile の再提示）                         | 完全に可逆                                                                                                                           |
| 3    | 待機時間の挿入・機能の一時制限（ゲスト発行の停止など） | 時間経過で自動解除                                                                                                                   |
| 4    | 一時停止（期限付き）                                   | 期限で自動解除。異議申立て可能                                                                                                       |
| 5    | 恒久停止                                               | **人間の判断を必須とする。** 根拠・判断者・期間を記録し、異議申立ての手段を提供する（[インシデント対応](./15-incident-response.md)） |

自動処理で到達してよいのは段階3までとする。段階4以上は人間が承認する。誤検知が判明した場合は、判定ロジックと閾値を見直し、その結果を[脅威モデル](./12-threat-model.md)と本書へ反映する。
