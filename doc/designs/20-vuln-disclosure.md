# 脆弱性の受付と継続的改善

> [設計ドキュメント索引](./README.md)

## 1. 受付窓口

公開後は、外部から脆弱性報告を受け付けられる窓口を用意する。窓口がなければ、報告者は報告する手段を持たず、結果として脆弱性は公表または悪用という形でしか表面化しない。

### 1.1 `/.well-known/security.txt`

[RFC 9116](https://www.rfc-editor.org/rfc/rfc9116) に従い、次を静的アセットとして配信する。

```
Contact: mailto:security@<ドメイン>
Expires: <1年後のISO8601日時>
Preferred-Languages: ja, en
Canonical: https://<ドメイン>/.well-known/security.txt
Policy: https://<ドメイン>/security-policy
```

- `Expires` があるため、**年1回の更新を運用タスクとして登録する**（期限切れは窓口不在と同義）。
- `security@` は通常の問い合わせ窓口と分離し、受信を確実に監視する。

### 1.2 公開ポリシー（`/security-policy`）

次を明示する。

| 項目                   | 内容                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| 対象範囲               | 本番ドメインと Worker。**stg 環境や第三者サービスは対象外**であることを明記                |
| 禁止事項               | 他ユーザーのデータへの実際のアクセス、サービス妨害、ソーシャルエンジニアリング、物理的攻撃 |
| 安全な調査の指針       | 検証は自身のアカウントで行う。ゲストアカウントは自由に作成してよい                         |
| 報告に含めてほしい情報 | 再現手順、影響、想定される攻撃者の利得                                                     |
| 対応の約束             | 下記の目標期間。誠実な報告に対して法的措置を取らないこと                                   |
| 報奨                   | MVP 期間中は金銭報奨なし。謝辞の掲載可否を報告者が選べること                               |

## 2. 対応の目標期間

| 段階                                 | 目標期間                         |
| ------------------------------------ | -------------------------------- |
| 受領の確認                           | 3営業日以内                      |
| 一次回答（再現可否と暫定的な重大度） | 7日以内                          |
| 重大度判定の確定                     | 14日以内                         |
| 修正（`critical` / `high`）          | 判定から30日以内                 |
| 修正（`medium` 以下）                | 次の計画的リリースに含める       |
| 公開判断（報告者との調整）           | 修正完了後、原則90日以内に公表可 |

重大度は[脅威モデル](./12-threat-model.md)の保護目的（P-1〜P-5）への影響で判定する。特に **P-5 秘匿性（確定前の相手布陣の漏えい）と P-1 公平性への直接的な影響は `critical` 相当**として扱う。

## 3. 報告受領後の処理

1. 受領を確認し、報告者へ返信する。
2. **証拠を保全する**（[インシデント対応](./15-incident-response.md) 2節）。既に悪用されている可能性があるため、報告＝インシデント対応の開始点として扱う。
3. 再現を確認する。再現できない場合も、報告者へ追加情報を求めたうえで記録に残す。
4. 悪用の痕跡がログにないか調査する。**あればインシデントとして 15 の手順へ移行する。**
5. 修正し、対応する[テスト](./19-testing.md)を追加する。
6. 報告者へ修正を通知し、公表の可否と時期を調整する。

## 4. 継続的改善

脆弱性・インシデント・重大な不具合・誤検知が発生した場合、**個別修正だけで終わらせない。** 次の4つへ必ず反映する。

| 反映先                             | 反映内容                                                           |
| ---------------------------------- | ------------------------------------------------------------------ |
| [脅威モデル](./12-threat-model.md) | 見落としていた脅威の追加、可能性・影響の見直し、残留リスクの再受容 |
| [テスト](./19-testing.md)          | 同じ問題を検出する自動テストの追加（回帰させない）                 |
| [監視](./14-observability.md)      | 早期に気づくための監視項目・閾値の追加または調整                   |
| 運用手順                           | 対応が遅れた原因が手順の不備にあるなら、手順そのものを改訂         |

## 5. セキュリティの到達目標

本設計におけるセキュリティの目標は、**強い制限を増やすことではない**。

> 通常の利用者には快適でありながら、不正利用を識別・制御でき、事故が起きても調査・復旧できる状態。

この基準に照らして、次のような変更は「セキュリティ強化」とは認めない。

- 通常の利用者に追加の操作を課すが、攻撃者にとっては迂回可能な対策
- 検知も記録もできないまま、機能だけを制限する対策
- 誤検知時に利用者が救済される経路のない自動停止

[設計原則](./01-principles.md)の「すぐ遊べることもセキュリティ要件として扱う」は、この目標の言い換えである。
