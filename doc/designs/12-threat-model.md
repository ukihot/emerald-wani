# 脅威モデルとリスク管理

> [設計ドキュメント索引](./README.md)

守るべき性質は [設計原則と保護目的](./01-principles.md) の P-1〜P-5 で定義した。本書はそれに対する脅威を列挙し、**対策後に残るリスクを誰がどの理由で受容したか**まで記録する。すべてのリスクを技術的に排除しようとはしない。

## 1. 記録の書式

各脅威は次の項目を持つ。**「対策を実装した」で終わらせず、残留リスクの受容者を必ず記入する。**

| 項目       | 説明                                                                 |
| ---------- | -------------------------------------------------------------------- |
| ID         | `T-<領域>-<連番>`                                                    |
| 守る対象   | 侵害される情報・機能と、対応する保護目的（P-1〜P-5）                 |
| 脅威       | 攻撃者が何をするか                                                   |
| 可能性     | 高 / 中 / 低（悪用の容易さと攻撃者の動機から判断）                   |
| 影響       | 高 / 中 / 低（発生した場合のユーザーと運営への損害）                 |
| 対策       | 実施する具体的な設計・実装。対応する[検証項目](./19-testing.md)の ID |
| 残留リスク | 対策後に残るもの                                                     |
| 受容       | 受容者・受容日・受容理由                                             |

受容者は MVP 期間中はプロジェクトオーナー（本リポジトリの管理者）とする。運営体制が拡大した際は改めて定義する。

### 受容にあたっての明示的な留保

1. **Cloudflare Access と WAF はアプリのコードで担保できない。** 管理画面の経路制限（T-AUTH-04）とエッジのレート制限（T-INFRA-01）は、本番・ステージングのデプロイ手順で設定して初めて成立する。設定前の本番公開は本受容記録の前提を満たさない。
2. **Turnstile はサイトキー・シークレットの投入が前提。** `ENVIRONMENT` が `development` 以外で `TURNSTILE_SECRET_KEY` が未設定の場合、ゲスト発行と認証系フォームは**すべて拒否**される（フェイルクローズ）。鍵の入れ忘れが「Bot 対策が黙って無効になる」形で現れないようにしてある。
3. **段階4以上の制裁（アカウント停止）は自動化していない。** 管理画面から1クリックで到達する導線も作っていない（[監視](./14-observability.md) 4節）。停止が必要な場合は[インシデント対応](./15-incident-response.md)の様式に従って人間が判断する。
4. **ip_hash は同日内の同一性判定にしか使えない。** ソルトが日次で変わるため、翌日以降の突き合わせはできない。長期の追跡を意図的に不能にした結果であり、調査時の制約として受け入れる。

## 4. 見直しの契機

脅威モデルは作って終わりにしない。次のいずれかが発生したら見直す。

- 重要な仕様変更（ランク戦・課金・チャットなど、新しい動機や攻撃面を生む機能の追加）
- インシデントの発生（[インシデント対応](./15-incident-response.md)の再発防止工程から必ず本書へ反映する）
- 依存する Cloudflare 機能の仕様変更
- 外部からの脆弱性報告（[脆弱性の受付](./20-vuln-disclosure.md)）
- 少なくとも半年に1回の定期レビュー

見直しの結果は、変更点と判断理由を本書の改訂履歴として残す。
