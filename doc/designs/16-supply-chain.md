# セキュアな開発と依存関係管理

> [設計ドキュメント索引](./README.md)

**ソースコードだけが攻撃対象ではない。** 依存パッケージ、CI/CD、ビルド環境、デプロイ権限も同じ保護対象として扱う（[脅威モデル](./12-threat-model.md) T-INFRA-03 / T-INFRA-04）。

## 1. 依存関係

### 1.1 再現可能なビルド

- `pnpm-lock.yaml` を**必ずコミットし、CI では `--frozen-lockfile` で導入する。** lockfile と `package.json` が乖離していたら CI を失敗させる。
- `package.json` の依存は範囲指定（`^`）を使うが、**実際に入るバージョンは lockfile が固定する。** 更新は意図的な PR としてのみ行う。
- Node.js のバージョンは `.node-version`（または `package.json` の `engines`）で固定し、CI とローカルで一致させる。`.npmrc` の `engine-strict=true` により不一致を検出する。

### 1.2 継続的な検査

| 検査             | 手段                                                                                                                     | 頻度          | 失敗時                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------- | ----------------------------------------------------------------------------------- |
| 依存の既知脆弱性 | `pnpm audit`                                                                                                             | PR ごと＋週次 | `high` 以上で CI 失敗                                                               |
| 依存の更新       | Dependabot（または Renovate）                                                                                            | 週次          | PR を自動作成                                                                       |
| 秘匿値の混入     | secret scanning（GitHub Advanced Security または `gitleaks`）                                                            | PR ごと       | 検出で CI 失敗し、該当シークレットを[即時ローテーション](./13-secrets-lifecycle.md) |
| 静的解析         | ESLint（`{@html}` 禁止など[セキュリティ規約](./11-security-controls.md)をルール化）、`svelte-check`、TypeScript `strict` | PR ごと       | エラーで CI 失敗                                                                    |
| SBOM 生成        | `pnpm licenses` ＋ CycloneDX 形式の SBOM をビルド成果物として保存                                                        | リリースごと  | —                                                                                   |

SBOM を残す目的は、将来の依存パッケージ侵害が公表されたときに**自分が影響を受けるかを即座に判定できる**ようにすることにある。

### 1.3 新規依存の追加基準

依存を1つ増やすことは攻撃面を1つ増やすことである。追加時は次を確認し、PR の説明に記載する。

| 観点             | 確認内容                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------- |
| 必要性           | 標準 API や既存依存で代替できないか。数十行で自作できるものではないか                       |
| 保守状況         | 直近1年のリリース、未解決の重大 issue、メンテナ数                                           |
| 権限             | インストールスクリプト（`postinstall`）を実行するか。実行する場合は理由を確認する           |
| 依存の広がり     | 推移的依存の数。1つ入れて数十個増えるものは慎重に判断する                                   |
| バンドルへの影響 | Worker のバンドルサイズとクライアントの初回表示への影響（[プラン制約](./03-tech-stack.md)） |

`.npmrc` の `allowBuilds` でビルドスクリプトの実行を明示的に許可したパッケージのみに限定する（現状は `esbuild` のみ）。

## 2. CI/CD

### 2.1 GitHub Actions の保護

- **外部 Action はコミット SHA で固定する。** タグ（`@v4`）はムーバブルであり、タグの付け替えによる乗っ取りを防げない。
  ```yaml
  - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
  ```
- `permissions:` をワークフロー単位で最小化する（既定では `contents: read`）。
- Pull Request からのワークフローに `pull_request_target` を使わない。使う場合はフォークのコードをチェックアウトしない。
- CI のログにシークレットを出力しない。`set -x` を有効にしたままシークレットを扱わない。

### 2.2 デプロイ権限の分離

| 環境       | デプロイ契機               | 必要な承認                                                          | 使用トークン                                          |
| ---------- | -------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------- |
| staging    | `main` へのマージ          | 不要（自動）                                                        | stg 用 Cloudflare API トークン                        |
| production | タグの作成、または手動実行 | **レビュー承認を必須**（GitHub Environments の required reviewers） | prod 用 Cloudflare API トークン（保護環境にのみ配置） |

- 本番用トークンは **GitHub Environments の保護環境**にのみ格納し、`main` 以外のブランチから参照できないようにする。
- Cloudflare API トークンは**最小権限**で発行する（Workers Scripts の編集、D1 の編集など、必要なスコープのみ。アカウント全体の権限を与えない）。
- トークンは90日でローテーションする（[鍵ライフサイクル](./13-secrets-lifecycle.md) S-05）。

### 2.3 デプロイ時の注意（Durable Objects）

デプロイは**進行中の全 Durable Object を再起動し、WebSocket を切断する**（[ルール版数の互換性](./06-rule-engine.md)）。したがって本番デプロイは次を守る。

- 対戦数の少ない時間帯に実施する。
- ルール実装を削除する変更は、[版数レジストリ](./06-rule-engine.md)の廃止条件を満たしていることを確認してから行う。
- デプロイ直後は再接続の集中と `client desync` を[監視](./14-observability.md)する。

## 3. ブランチとレビュー

- `main` への直接 push を禁止し、PR 経由に限定する。
- PR には CI の全ジョブ通過を必須とする。
- セキュリティに関わる変更（認証、認可、射影、チケット、CSP、レート制限）は、変更内容に対応する[テスト](./19-testing.md)の追加または更新を必須とする。
- 本番デプロイを実行できる人物と、コードをレビューする人物を分離できる体制になった時点で、両者を別にする。MVP 期間中に1人で兼ねる場合は、その事実を[脅威モデル](./12-threat-model.md)の残留リスクとして記録する。
