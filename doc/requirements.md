# エメラルドワニ 要件定義

- 版数: 2.0
- 改訂日: 2026-09-03
- ゲームルールの正本: [ルールブック](./designs/05-game-rules.md)

## 1. 概要

「エメラルドワニ」は、両プレイヤーが同じ8体のワニを使い、敵を捕獲して巣へ運び、捕食して得点する1対1オンライン盤面ゲームである。

カードゲームではない。デッキ、手札、ドロー、レアリティ、試合中のランダム効果は持たない。ランダム性は試合前のニュートラルゾーン生成に限定し、布陣公開後は完全情報ゲームとする。

## 2. プロダクト目標

- ブラウザだけで短時間に遊べる、公平な1対1対戦を提供する。
- 同一の駒条件のもと、地形理解、布陣、移動、護送、救出の判断で勝敗が決まるようにする。
- ゲストとしてすぐ遊べ、本登録後は戦績と設定を継続利用できるようにする。
- PCとスマートフォンの双方で盤面と駒状態を明確に把握できるようにする。
- サーバ権威型と決定論的リプレイにより、不正操作の拒否と対戦結果の検証を可能にする。

## 3. 対象ユーザー

- 短時間の対戦型ボードゲームを好むユーザー
- ランダムドローや所持資産差のない競技ゲームを求めるユーザー
- 複雑なデッキ構築なしに、位置取りと読み合いを楽しみたいユーザー
- PCまたはスマートフォンのブラウザから手軽に遊びたいユーザー

## 4. ゲーム要件

詳細は[ルールブック](./designs/05-game-rules.md)を正とする。本章は実装範囲の要約であり、矛盾する場合はルールブックを優先する。

### 4.1 対戦条件

- 1対1の交互手番制とする。
- 両者はヌシワニ、カツギワニ、ポチャワニ、ビヨーンワニ、ナナメワニ、セッカチワニ、トビワニ、コワニを各1体使う。
- 特殊ワニの捕食は1P、コワニの捕食は0Pとする。
- 3P先取、30ラウンド時の得点比較、同一局面3回、投了、連続時間切れで終局する。

### 4.2 盤面

- 両陣営の固定ゾーンと、試合ごとに生成するニュートラルゾーンで構成する。
- 通常マス、木、沼、巣を表現する。
- 盤面は180度回転対称で、通行可能マスの連結性と複数経路を保証する。
- 同一 seed と `MAP_VERSION` から同一盤面を再現する。
- 生成盤面は布陣前に両者へ公開し、対局中は変更しない。

### 4.3 布陣

- 両者は45秒以内に自分の8体を味方ゾーンへ配置する。
- 相手の配置は確定前に見せず、両者確定後に同時公開する。
- 時間切れ時は最後の有効配置を使い、未配置分を決定論的に自動配置する。

### 4.4 ターン

- 通常は毎ターン2活力、先手の初回だけ1活力とする。
- 活力は持ち越さない。
- 移動、噛みつき、ジャンプ、沼ワープ、運搬、捕食をルールどおり検証する。
- 1ターン30秒とし、時間切れ時は残り活力を失って自動終了する。

### 4.5 捕獲サイクル

- 噛みつきで敵を捕虜にし、運搬役と同じマスへ重ねる。
- 運搬役には噛みつき、ワープ、ジャンプ、固有能力、複数捕虜保持を許さない。
- 敵の運搬役を噛むと、ルールに従って捕虜を救出する。
- 自分の巣で2活力を使った時点で捕食と得点を確定する。

## 5. ゲームモード

MVPでは次を提供する。

- CPU練習戦
- ランダムマッチ
- 招待コードによるフレンド対戦
- 対戦履歴とリプレイ

ランク戦、シーズン、観戦、チャットはMVP対象外とする。

## 6. 画面要件

- ランディング、「すぐ遊ぶ」、登録／ログイン、ホーム
- 対戦モード選択とマッチング待機
- 盤面確認と布陣
- 対戦画面
- 結果、履歴、リプレイ
- 設定
- 管理画面

対戦画面は盤面、ゾーン、地形、巣、全ワニ、捕虜、得点、活力、手番、ラウンド、残り時間を同時に判別可能にする。

## 7. UX・アクセシビリティ

- マウス、タッチ、キーボードで全主要操作を完結できる。
- 合法手と対象を視覚的に示すが、正の判定はサーバが行う。
- 色だけで地形、所有者、選択状態、捕虜状態を区別しない。
- タップ対象は44×44 CSS px以上を基本とする。
- `prefers-reduced-motion` とゲーム内の演出軽減設定に対応する。
- 再接続中、相手切断中、サーバ同期待ちを明示し、誤操作を防ぐ。

## 8. アカウントと認証

- 未登録ユーザーは「すぐ遊ぶ」から匿名の認証済みゲストとして参加できる。
- ゲストと本登録ユーザーで対戦ルール、使用駒、マッチング条件を変えない。
- ゲストは本登録へ昇格でき、戦績と設定を安全に移行できる。
- 本登録はメールアドレスとパスワードを基本とする。
- 管理者はMFAを必須とし、管理経路を一般ユーザーから分離する。

## 9. オンライン対戦

- 1試合を1つの MatchRoom Durable Object が所有する。
- クライアントは行動要求だけを送り、結果を指定できない。
- サーバはフェーズ、手番、所有権、活力、地形、移動規則、対象、捕虜状態を再検証する。
- Command は `actionId` で冪等化し、`baseRev` で古い状態からの操作を拒否する。
- 切断後は短命WSチケットを再取得して復帰できる。
- 進行中の対戦状態を Durable Object のSQLiteへ永続化する。

## 10. 情報公開

- 盤面生成後の地形と `MAP_VERSION` は両者へ公開する。seed 自体の公開時期は実装前に確定する。
- 布陣中は相手の配置を秘匿する。
- 両者の布陣確定後は全ゲーム情報を公開する。
- 運営ログにも、公開前の相手布陣を通常ログとして出力しない。
- 終局後のリプレイは完全情報として保存・配信できる。

## 11. 決定性と版数

- `RULE_VERSION` で駒、行動、勝敗判定を固定する。
- `MAP_VERSION` で固定ゾーンと盤面生成アルゴリズムを固定する。
- seed、両版数、先手、Command 列から同一の対戦を再現できるようにする。
- 進行中の試合と保持期間中のリプレイに必要な旧版実装を削除しない。
- 対局中のルール処理で乱数を使用しない。

## 12. セキュリティ

- Cookie は `HttpOnly`, `Secure`, `SameSite=Lax` を用いる。
- RESTとWSの入力を厳格なスキーマで検証し、未定義キーを拒否する。
- WSチケットは短命、署名付き、単回使用とする。
- 他人の試合、履歴、リプレイへのアクセスを拒否する。
- ゲスト発行、マッチング、WSチケット、通報、一般APIにレート制限を設ける。
- 管理画面はMFAとCloudflare Accessで保護し、操作を監査する。
- Cookie、認証情報、メールアドレス、生のIP・User-Agentをアプリログへ出さない。

## 13. データとリプレイ

- D1にはユーザー、プロフィール、対戦結果、参加者、招待、監査、通報、お知らせを保存する。
- カード所有やデッキ構成のデータは保存しない。
- 対戦中の Command/Event は MatchRoom に保持し、終局後にR2へ圧縮保存する。
- Queueには対戦IDだけを送り、consumerが内部exportからリプレイを取得する。
- R2保存成功の確認前に MatchRoom の状態を削除しない。

## 14. 非機能要件

### 性能

- プレイヤー操作への確定応答は通常時500ms以内を目標とする。
- 盤面初期表示後の操作で大きなレイアウトシフトを起こさない。
- 画像・音声は必要解像度に最適化し、遅延読み込みする。

### 可用性

- Worker再起動やWebSocket切断後も、永続化済みrevから再接続できる。
- D1とR2のバックアップ、復元試験、環境分離を行う。
- 終局ログのアーカイブ失敗を検知し、自動再試行と運営通知を行う。

### 対応環境

- 最新2世代のChrome、Edge、Firefox、Safariを対象とする。
- iOS SafariとAndroid Chromeの現行主要版を対象とする。

## 15. テスト受け入れ条件

- 8種すべての移動・噛みつき・固有能力に単体テストがある。
- 捕獲、運搬、救出、捕食の通常系と境界ケースを網羅する。
- 大量 seed に対して全盤面生成条件をプロパティテストする。
- 同じ seed と版数から同じ盤面・最終状態を再現できる。
- 布陣確定前の全送信データに相手配置が含まれない。
- 30ラウンド、同一局面3回、投了、時間切れの終局条件を検証する。
- CPU戦とオンライン戦が同じルールエンジンを使う。
- ゲスト開始から終局・履歴確認までE2Eで完走する。

## 16. MVP対象外

- デッキ構築、カード収集、パック、レアリティ
- 試合中のランダム効果
- 駒性能に影響する課金・アンロック
- ランク、シーズン、報酬
- 観戦、チャット、大会機能
- ネイティブアプリ

## 17. 実装前の未決事項

ルールエンジンへ着手する前に、[ルールブック末尾の解釈事項](./designs/05-game-rules.md)を確定する。特に盤面座標、巣、コワニの向き、巣への距離関数、ポチャワニが参照する移動種別、同一局面キー、生成アルゴリズムは実装とテストデータ構造へ直接影響する。
