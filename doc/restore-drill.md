# 復元試験の手順と実施記録

> 設計上の根拠: [障害対策と可用性](./designs/18-availability.md) 15.2 / 15.4

「バックアップがある」だけでは復旧できない。**四半期ごとに実際に復元を実行し、所要時間と発見事項を本書へ残す。**

## 1. 何から復元するのか

| 復元元                 | 保持                          | 使いどころ                                         |
| ---------------------- | ----------------------------- | -------------------------------------------------- |
| D1 Time Travel         | 無料プランで7日（プラン依存） | 直近の誤更新・誤削除からの巻き戻し                 |
| 週次エクスポート（R2） | R2 の保持設定に従う           | 7日を超える期間の復旧。監査ログ（保持400日）はこれ |

週次エクスポートは realtime Worker の Cron（`0 4 * * 1`、月曜 04:00 UTC）が実行し、`r2://emerald-wani-replays/exports/<YYYY-MM-DD>/` へ次を書く。

- `manifest.json` … 書き出し時刻と表ごとの件数（**復元後の突き合わせに使う**）
- `<table>.ndjson.gz` … 表の全行（NDJSON + gzip。行単位で読めるため部分破損に強い）

対象は `match` / `match_player` / `player_profile` / `report` / `security_event` / `admin_audit` と、`user` の復旧に必要な列のみ。実装は [`workers/realtime/src/export.ts`](../workers/realtime/src/export.ts)。

## 2. 手順

**本番データは使わない**（18-availability 15.2）。staging に同等規模のダミーデータを入れ、本番と同じ手順で復元する。

```bash
# 0. 前提: 対象環境のマイグレーションが適用済みであること
pnpm db:migrate:stg

# 1. 復元（既定はローカル。staging へは --target と --remote を付ける）
pnpm restore:drill -- --date 2026-09-07 --target emerald-wani-db-stg --remote

# 2. 復元後にアプリが動くことを確認する
pnpm verify:phase5     # ゲスト開始→本登録→対戦→履歴・リプレイ
pnpm verify:phase6     # ヘッダー・管理画面・ゲスト発行の門・監査・エクスポート
```

`scripts/restore-drill.mjs` は次を行う。

1. `manifest.json` を取得して「何が何件あるはず」かを確定する
2. 各表の NDJSON を `INSERT OR REPLACE` へ変換して D1 へ流す（途中で失敗しても再実行できる）
3. 復元後の件数をマニフェストと突き合わせ、**足りなければ異常終了する**
4. 所要時間を出力する（[RPO/RTO](./designs/18-availability.md) 15.4 と比較する）

## 3. 判定基準

| 対象                     | RTO    | 判定                                           |
| ------------------------ | ------ | ---------------------------------------------- |
| ユーザー・アカウント情報 | 4時間  | 手順完了までの実測がこれを超えたら手順を見直す |
| 対戦結果                 | 8時間  | 同上                                           |
| 監査ログ                 | 72時間 | 同上                                           |
| 件数の一致               | —      | マニフェストの件数を下回ったら**不合格**       |
| 復元後の動作             | —      | `verify:phase5` / `verify:phase6` が通ること   |

## 4. 実施記録

| 実施日     | 環境  | 担当                 | 復元元             | 所要 | 結果 | 発見事項                                                                                                                 |
| ---------- | ----- | -------------------- | ------------------ | ---- | ---- | ------------------------------------------------------------------------------------------------------------------------ |
| 2026-09-07 | local | プロジェクトオーナー | exports/2026-09-07 | 30秒 | 合格 | 初回。手順とスクリプトを整備。`user` は個人情報を含むため復元対象から外しており、アカウント復旧は Time Travel に依存する |

次回予定: 2026-12（四半期ごと）。staging での実施を1回以上含めること。

## 5. 既知の限界

- `user` テーブルはエクスポートで**列を絞っている**（メール・パスワードハッシュを R2 へ複製しない方針）。認証情報の復旧は D1 Time Travel の範囲（無料プランで7日）に限られる。7日を超える障害では、利用者にパスワード再設定を依頼する運用になる。
- R2 のリプレイ本体はエクスポートに含めない。`match.replay_key` の再照合（Cron）で再生成する経路が別にある（[18-availability](./designs/18-availability.md) 15.4）。
- 復元スクリプトは `INSERT OR REPLACE` で冪等だが、**復元先に既にある新しい行は上書きされる**。本番へ流す前に必ず影響範囲を見積もること。
